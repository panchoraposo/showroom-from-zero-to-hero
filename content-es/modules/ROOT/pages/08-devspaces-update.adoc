= Actualizar código con Dev Spaces

Este módulo recorre el flujo **editar en IDE web -> commit a Gitea -> pipeline Tekton -> nuevo despliegue**, usando **Red Hat OpenShift Dev Spaces** y el componente **neuralbank-backend**.

== Abrir el componente en Developer Hub

. Inicia sesión en **Developer Hub**.
. Busca **neuralbank-backend** en el **Catalog** y abre su página.
. Haz clic en **Open in Dev Spaces** (o la acción equivalente del plugin).

Si el botón no aparece, copia la URL del repositorio desde Gitea y crea el workspace en Dev Spaces manualmente.

== Esperar a que el workspace inicie

. Espera a que el **DevWorkspace** llegue a estado **Running**.
. Abre el IDE en el navegador.

El workspace usa el `devfile.yaml` generado por el template:

[source,yaml]
----
schemaVersion: 2.2.2
metadata:
  name: neuralbank-backend
components:
  - name: tools
    container:
      image: registry.redhat.io/devspaces/udi-rhel9:latest
      memoryLimit: 4Gi
      cpuLimit: "2"
      mountSources: true
commands:
  - id: 01-build
    exec:
      component: tools
      commandLine: <...>
      workingDir: ${PROJECT_SOURCE}
  - id: 02-run
    exec:
      component: tools
      commandLine: <...>
      workingDir: ${PROJECT_SOURCE}
----

== Desarrollar en Dev Spaces (tasks del devfile)

En esta sección usarás Dev Spaces para inspeccionar el devfile, escanear dependencias con RHDA, compilar y ejecutar la app, acceder a Quarkus Dev UI + Swagger, hacer un pequeño cambio y pushearlo a Git.

.1. Revisar el `devfile.yaml`
. Abre `devfile.yaml` en la raíz del repositorio.
. Léelo e identifica las piezas clave:
* Recursos del contenedor (CPU/memoria) bajo `components[].container`.
* Los comandos disponibles (aparecen como tasks) y qué hacen:
** `01-build` ejecuta `mvn compile -DskipTests`
** `02-run` ejecuta `mvn quarkus:dev` para live reload
. Abre también `.mvn/maven.config` y `.mvn/settings.xml` para ver cómo Maven está configurado para usar el Nexus in-cluster.

== Dependency Analytics (RHDA) en Dev Spaces

Este paso usa la extensión *Red Hat Dependency Analytics* (RHDA) para escanear `pom.xml` y generar un reporte de dependencias/vulnerabilidades.

.2. Activar RHDA y revisar `pom.xml`
. Abre `pom.xml`.
. Asegura que la extensión *Red Hat Dependency Analytics* esté habilitada:
* Abre la vista *Extensions*.
* Busca `Dependency Analytics` (publisher `redhat`, extensión `fabric8-analytics`) y actívala/instálala si es necesario.
. Genera el reporte:
* Click derecho en `pom.xml` y ejecuta *Red Hat Dependency Analytics Report...* (o usa la command palette).
. Revisa el reporte y comenta algunos hallazgos:
* *Por qué aparecen CVEs*: a menudo por dependencias **transitivas** traídas por un framework (Quarkus, Netty, Jackson, etc.).
* *Severidad vs explotabilidad*: la severidad es un punto de partida; el contexto importa (exposición de red, paths alcanzables, configuración).
* *Remediación*: suele ser mejor actualizar plataforma/BOM y verificar que cambie el árbol de dependencias.

== Compilar y ejecutar en el workspace

El proyecto expone build y run como **tasks del devfile**.

.3. Compilar el backend usando el task del devfile
. Abre la command palette y ejecuta `Tasks: Run Task`.
. Selecciona `devfile: 01-build`.
. Espera a ver **BUILD SUCCESS**.

.4. Ejecutar el backend usando el task del devfile
. Abre la command palette y ejecuta `Tasks: Run Task`.
. Selecciona `devfile: 02-run`.
. Déjalo corriendo para habilitar live reload.

.5. Abrir Quarkus Dev UI y Swagger UI
. Cuando `devfile: 02-run` está corriendo, Dev Spaces debería detectar que Quarkus escucha en el puerto `8080`.
. Abre el endpoint:
* Usa el prompt del IDE para abrir el puerto `8080` (recomendado), o
* Abre la vista *Ports/Endpoints* y abre/expone el puerto `8080`.
. Abre Quarkus Dev UI en `/q/dev-ui/`.
. Desde Dev UI, abre **Swagger UI** (o ve directo a `/q/swagger-ui/`).

== Hacer un cambio de código

.6. Modificar código y verificar live reload + refresh de Swagger
. Abre `src/main/java/com/neuralbank/api/CreditResource.java`.
. Agrega un endpoint simple bajo `@Path("/api")`:
+
[source,java]
----
@GET
@Path("/hello")
@Produces(MediaType.TEXT_PLAIN)
public String hello() {
    return "hello from workshop";
}
----
+
. Guarda el archivo y mira el terminal de `02-run`; Quarkus debería recompilar automáticamente.
. Vuelve a Swagger UI y verifica que aparezca y funcione el nuevo endpoint `GET /api/hello`.

== Commit y push a Gitea

.7. Commit y push desde Dev Spaces
. Usa la vista *Source Control* del IDE para hacer stage del cambio, crear un commit y hacer push.
. Alternativamente, usa el terminal:

[.console-input]
[source,bash]
----
git status
git add <modified-files>
git commit -m "workshop: demo change from Dev Spaces"
git push origin main
----

== Ver la Tekton Pipeline

. Ve a **OpenShift Console -> Pipelines -> PipelineRuns** en el proyecto `{user_name}-neuralbank`.
. Identifica un nuevo run disparado por el push reciente.

El webhook de Gitea usa una URL interna de servicio para gatillar el EventListener:

----
http://el-neuralbank-backend-listener.{user_name}-neuralbank.svc.cluster.local:8080
----

Esto evita problemas de TLS con certificados self-signed del cluster.

== Verificar el despliegue de la nueva versión

. En **Workloads -> Pods**, confirma que el Deployment hizo un rollout (pods nuevos con timestamp reciente).
. Después de que termine el PipelineRun, verifica que el Route *desplegado* también tenga tu cambio.

[.console-input]
[source,bash,subs="attributes+"]
----
export APP_NAME="${APP_NAME:-neuralbank-backend}"
export NS="{user_name}-neuralbank"
export APIKEY_NAME="{user_name}-${APP_NAME}"

SECRET_NAME=$(oc get apikey -n "$NS" "$APIKEY_NAME" -o jsonpath='{.status.secretRef.name}')
API_KEY=$(oc get secret -n "$NS" "$SECRET_NAME" -o jsonpath='{.data.api_key}' | tr -d '\n' | base64 -d)

curl -s -H "X-API-Key: $API_KEY" \
  "https://neuralbank-backend-{user_name}-neuralbank.{cluster_domain}/api/hello"
----

Deberías ver el cambio reflejado en la respuesta.

== Bonus: Editar el MCP Server en Dev Spaces (customer-service-mcp)

El workshop también incluye el componente **Customer Service MCP**. Puedes editarlo y ejecutarlo en Dev Spaces, y validar los endpoints MCP que exponen sus tools.

. Abre el componente en Developer Hub:
* Ve al Catalog y abre **customer-service-mcp**
* Haz clic en **Open in Dev Spaces**
. Espera a que el workspace esté listo (mismo flujo que el backend).
. Ejecuta el MCP server en modo dev:
* `Tasks: Run Task` → `devfile: 02-run`
. Abre Quarkus Dev UI:
* Abre el puerto `8080`
* Visita `/q/dev-ui/`
. Valida endpoints MCP (desde el terminal de Dev Spaces):
+
[.console-input]
[source,bash]
----
curl -s "http://localhost:8080/q/health" | jq .
# SSE endpoint (stream de eventos)
curl -i -N "http://localhost:8080/mcp/sse"
----
+
. Recomendado: usa Quarkus Dev UI para invocar tools:
* En Dev UI, abre *MCP Server - HTTP/SSE - Tools*
* Selecciona una tool (por ejemplo `getCustomer`) y haz clic en *Call* para ver la respuesta

== Resumen

Demostraste el ciclo completo **Dev Spaces -> Git -> Tekton -> OpenShift**, alineado con GitOps y la tarjeta del componente en Developer Hub. Los desarrolladores trabajan en un ambiente consistente mientras la plataforma aplica estándares y automatización.
